# Parser 三方综合对比报告

比较日期：北京时间2026年10月15日。范围：官方 cyTimes、rsTimes Rust Parser、cyTimes-rewrite Cython Parser。仅比较已选定产物，本轮没有修改解析实现、替换交付版本或发布。

## 先看结论

- **常规功能：三方在5,432个场景中，经列明的包名／类名对应后结果一致。** 包括从原项目提取的728条日期字符串及六种配置，共4,368个组合；另有扩展解析、配置操作、子类和回调等。比较包含返回类型、日期时间字段、时区、fold，以及普通错误的类别、文字和原因。
- **接口和边界仍有差异。** Cython配置类叫`Config`，官方和Rust叫`Configs`；两个重构版本均未提供原版`Parser`、`timelex`、`parse_obj`。异常输入还存在错误类别及文字差别，尤其Rust会把`1:4294967297`解释成`4294-04-06`，Cython明确拒绝。这一项应优先核查。
- **性能：完成全部58项的直接三方观察，不能当作新的正式性能验收。** 每项都实际调用三个已核对的原生产物，没有用两份历史报告相除。固定预试未建立充分稳定性，故停止正式采集；随后在预算内作一次完整、固定的诊断调查。下表用于了解差异方向，不能凭它认定稳定胜负或替换原正式成绩。
- **原有验收不变。** Rust此前相对官方的两轮36项parse组合为1.8208／1.8244倍，正式通过；这是另一套已保存证据，并非本轮三方成绩。Configs独立设置允许为parse让步，只报告速度。

## 3. 功能差异逐条说明

### 3.1 类名与导入路径不同

官方、Rust使用`Configs`，Cython使用`Config`。配置公开成员名称一致，调用方迁移时需要改import／类名。三个包的模块路径不同，因此不能假定一个包保存的pickle能够被另一个包直接读取。各自的基本保存和读取已比较，跨包迁移不在本轮范围。

### 3.2 只保留Config(s)与parse，未提供原版辅助接口

原版模块还能访问`Parser`、`timelex`和`parse_obj`；两个重构包都没有提供。这与本轮函数式重构范围一致。如果用户代码只调用`parse`并设置配置，不受这项影响；直接使用这些辅助接口的代码需要迁移，不能宣称整个原parser模块完全替代。

### 3.3 超长年份：都安全拒绝，错误文字不同

```python
parse("9" * 40)
```

Rust和Cython均抛出`ParserFailedError`，其原因都是`OverflowError`。Rust说明读取年月日时整数溢出；Cython说明十进制值超过无符号64位范围。按错误类别捕获时含义接近；精确匹配错误文字的代码会受到影响。

### 3.4 极长小数：都安全拒绝，错误文字不同

```python
parse("12." + "9" * 40 + "h", default=date(2024, 1, 1))
```

同样均为`ParserFailedError`，原因是`OverflowError`，但原因文字不同。这里比较的是异常输入的安全处理，不是普通小数秒不兼容。

### 3.5 极端时区配置：拒绝的异常类别不同

```python
Configs().add_tz("huge", hours=2**30)  # Cython调用使用Config类名
```

Rust抛出`OverflowError`；Cython抛出自己的`InvalidConfigsValue`，提示换算后的时区秒数超出范围。两者均拒绝输入，但调用方如果只捕获其中一个异常类别，迁移后就可能漏捕获。

### 3.6 错误恢复状态：长度错误的类别不同，类型错误的文字不同

| 输入 | Rust | Cython |
| --- | --- | --- |
| `cfg.__setstate__(())` | `ValueError`，状态长度不对 | `TypeError`，要求19或20字段元组 |
| `cfg.__setstate__(None)` | `TypeError`，要求tuple | `TypeError`，要求19或20字段元组 |

这主要影响手工恢复错误状态和损坏数据的错误处理。它不等于正常pickle恢复失败，也不需要为了跨项目对比而统一两包的内部状态格式。

### 3.7 超宽分钟输入：Rust接受并重新解释，Cython拒绝

```python
parse("1:4294967297", default=date(2024, 1, 1))
```

- Rust返回`datetime(4294, 4, 6)`。
- Cython抛出`ParserFailedError`，原因是`OverflowError`。

这比错误文字差异更值得关注：看起来像时间的输入被Rust解释成了另一个日期。本轮证据没有证明Rust发生了整数回绕，不能把它直接称为“Rust整数回绕”；为何这个异常时间被重新解释成日期，仍应作针对性核查。建议下一轮先明确该边界应拒绝，再用一条针对性用例修正。本轮只比较、记录，不改变选定产物。

**以上六项安全／错误状态输入没有再次运行官方包。** 它们位于既有记录中的不安全算术或状态读取边界，因此表中只陈述两个重构包的实测结果，不编造官方输出；具体原版是否崩溃或返回某值，本轮没有重新验证。

## 4. 性能怎么读

下表全部是**本轮实际三方配对的诊断观察**。速度比定义如下：

- Rust相对官方＝官方耗时÷Rust耗时。
- Cython相对官方＝官方耗时÷Cython耗时。
- Rust相对Cython＝Cython耗时÷Rust耗时。

三个列都以大于1表示列中实现更快。比如Rust相对Cython为1.25×，意味着Rust速度约为1.25倍、耗时少20%；0.80×意味着Rust耗时多25%。不能把“速度快25%”和“耗时少25%”混用。

### 从观察值看，差异集中在哪里

- **普通parse整体：** 36项等权组合观察到Rust相对官方1.836倍、Cython相对官方1.642倍，Rust相对Cython约1.118倍。最后一项对应Rust耗时约少10.6%，还不能当成稳定承诺。
- **Rust更值得关注的方向：** 通用解析、自定义／自然语言月份、时区文字和带默认值的解析。其中ISO文字强制走通用解析约1.866倍，长小数秒搭配默认日期约1.618倍，均为本轮观察值。
- **Cython更值得关注的方向：** 常用ISO格式；Rust相对Cython组合为0.892倍，按观察值换算，Rust耗时约多12%。真实Pydt构造为0.959倍，差距较小，尤其不宜凭本次波动直接断言优劣。
- **日期顺序类接近：** 组合约1.007倍；这样的小差异低于当前波动，实际结论应视为暂不能区分。
- **配置设置差距更大：** 17项配置独立调用中，Rust相对Cython组合约0.447倍。默认配置构造的单次平均观察值约为Rust43.6微秒、Cython2.78微秒；这与parse本身的组合成绩分开报告。此前已明确允许Configs设置性能为parse让步，不能把它混入36项parse组合。
