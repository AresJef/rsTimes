# Delta 第三轮开发复盘：以时间约束推动快速优化、快速迭代

日期：2026-10-13。

本复盘依据已完成的时间审计、计划、台账和候选97收尾记录。只整理已有证据，不恢复优化、构建或测试。本文提出后续项目的执行原则，不追溯修改本轮门槛，也不把未完成的验收改记为通过。

## 1. 总体判断

本轮交付了真实的功能改进和性能优化，但没有实现原来8小时内完成的开发目标，原计划的完整双轮性能验收也没有全部通过。最终按照用户指令，采用合理成果、如实更新验收状态并结束推进。

最需要改进的是执行效率：分析过长、候选变更带来的重验成本过高、测试总工作量与时间预算没有充分匹配。安全和正确性有必要保护，但不应把每一种可能性都扩展成新调查、新测试或新工具。

**未来以“快速优化、快速迭代”为核心指导。项目计划时间是实际执行约束；所有新增测试和额外步骤，都必须计入预算，并证明它们能够直接缩小当前目标缺口。** 已批准增加时间，只是扩大可执行额度，不能证明原估计合理，也不能成为继续低效路径的理由。

## 2. 本轮取得了什么，仍缺少什么

最终采用版本为 `0.1.0+delta.3`，候选97。源码与实际安装包一致，保留了不可变构造、同类比较、受检查的小数和64位输入、`apply_many()`、精确 `to_timedelta()`，以及表示、日期计算、Delta算术、批量模式和构造等优化。没有可靠收益的实验已撤回。

功能差分、行为契约、文档示例、Rust检查及独立源码包重建安装已通过。候选97完整主周期的143个性能场景，数值门槛全部达到；既有核心相对上一版Rust的中位速度比为1.080，相对cyTimes 3.1.0为1.656。核心批量组也达到约定的1.50倍门槛。这些结果支持采用现有优化，但不能代替完整正式验收。

主周期仍有两项波动超过5%：缓存哈希场景约5.209%，NumPy反向减法场景约6.631%。候选97的完整独立周期、双轮原始数据审计及最新demo实际运行未执行。原严格验收分值保留73/100，没有改成100%。用户批准直接收尾，是采用决定，不是对缺失证据的补认。

这次正确保留了失败、慢样本和未完成状态。需要改善的是更快地产生可交付的结论，而不是让结论看起来更好。

## 3. 时间到底花在哪里

原计划480分钟。扣除已确认的等待和停止后，修正的保守计时总额为 **1692.44分钟，约28小时12分钟，是原计划的3.53倍**。历次增加额度得到用户授权，不应描述为未经授权超额。

该总额仍含276.46分钟未准确归类，不能把全部1692.44分钟称为已经证明的有效开发时间。

| 实际运行状态 | 约分钟 | 占保守总额 |
| --- | ---: | ---: |
| 命令运行之外的分析、设计推演和结果判断 | 690.4 | 40.8% |
| 性能脚本运行，包括定位、开发比较、控制、正式采集及调度 | 653.6 | 38.6% |
| 上下文整理与恢复 | 39.1 | 2.3% |
| 简报、交付文字、可识别的构建检查及其他命令 | 33.0 | 2.0% |
| 未准确归类的间隔 | 276.5 | 16.3% |

分析时间包含必要的实现设计和失败定位，不能全部认定无效。性能运行也包含多种工作，不能当作纯计时循环。构建与检查的设计时间分布在其他分类中，不能根据较短的命令执行窗口认定它们总共只花了十几分钟。

能够完整还原的后期窗口约7小时45分钟：优化定位、开发和定向核查176.53分钟；审查和重建安装14.02分钟；控制及校准104.58分钟；正式测试和处理170.26分钟。**控制与正式测试合计约占该窗口59.1%。** 这是同一段时间的另一种划分，不能与上表重复相加。

最终97的控制和主周期实际采集合计96.96分钟；92的控制、主周期和独立周期合计140.55分钟。不同候选反复进入完整验证，是可确认的大额成本。

## 4. 为什么时间不断扩大

### 4.1 估计了修改代码的时间，没有充分估计让修改能够交付的时间

一次优化不仅是改几行Rust，还可能需要重新构建、确认加载新包、检查相关行为、核查性能，再对新产物完成正式验收。后期一次完整主周期已经需要约44分钟，完整控制约53分钟。新候选不能借用旧候选的正式成绩，因此几分钟的代码修改可能带来远大于修改本身的后续成本。

重新验证不同产物本身并非重复劳动。应减少的是在缺少充分开发确认时进入完整验证，以及后期不断改变最终候选造成的重验。

### 4.2 样本方案足够严格，但没有充分证明适合快速项目的预算

143个正式场景，每项12×120组，意味着一个完整周期需要205,920个完整配对组，还需要不同实现的独立测量、预热、记录和失败回队。短批次降低了单次受干扰的概率，却不自动缩短全部采集。

这些数量不是临时人为逐项测出来的，脚本已自动执行。问题在于没有在早期用代表场景的实际接收速度，充分核算整个矩阵、完整控制、两轮测试及必要修复能否装入预算。不能事后为了通过而减少样本；未来应在正式采集之前，用测量精度和预算共同确定并冻结方案，不直接继承上一项目的数量。

### 4.3 分析与决策周转过长

约690分钟的分析独占时间，不能用CPU波动解释。必要思考之外，持续比较更多实现路径、推演尚未出现的边界、反复解释和核对，都会推迟下一个可以验证的结果。

由此作出的执行判断是：每次分析应迅速形成一个有证据的改动或停止决定。无法证明某个问题当前存在，或者不能说明它与目标缺口的关系，就不应继续扩大调查。不能仅因为一种优化在理论上可能更快，就投入完整开发和验证。

### 4.4 进度检查没有足够强地改变低效路径

本轮记录了进度、超时和重新分配时间，但反复超时后，检查容易变成“为什么继续，以及还要多少时间”的说明。方向与目标有关，不代表当前方法成本合理。

早期批量优化及小数与既有性能保护修复两阶段，原预算合计70分钟，历史累计已达411.19分钟。这包含其分析、构建和测量，不是纯编码时间。如此大的偏差需要改变解决方法或停止低收益分支，不能主要依靠继续延长预测。

### 4.5 全局额度与局部采集上限没有充分协调

候选97末尾仍有两项噪声缺口，但已有控制和正式采集接近阶段上限。剩余局部额度装不下需要的完整补测，即使项目总账还有时间，也不能直接完成。

真正需要固定的测量质量规则应保留；阶段时间分配则应区分目标额度和确有必要的硬上限。不能在缺少收尾余量时启动完整流程，再到末尾依赖额外授权。合理的校准次数授权也不能代替对完整收尾成本的核算。

### 4.6 时间记录不够统一

前段步骤表合计674.40分钟，后续用时又分布在其他阶段和检查记录中。它可以追溯，却不能直接展示完整分布。最终仍有16.3%的时间不能准确归类，说明当时台账不够闭合。

后续应继续使用唯一台账，按活动切换记录主要用途；并行重叠只算一次，等待单列。无需增加第二个看板或复杂计时系统，也不需要逐条记录所有工具调用。

## 5. 减少防御性行为，具体减少什么

减少防御性行为，指减少没有足够依据、收益和时间边界的扩展工作，不是删除必要保护。

| 情况 | 后续执行方式 |
| --- | --- |
| 源码、输入、环境及风险均未变化，已有有效证据 | 复用证据，不重复完整调查或检查。 |
| 改动涉及日期边界、溢出、Python引用或子类调用 | 针对实际受影响行为检查，满足后停止扩展。 |
| 只有理论上可能出现的新边界，没有复现或直接影响 | 记录为后续事项；除非属于必须保护的已知安全风险，不扩展本轮。 |
| 一个已知慢点还没解决，却准备增加通用工具能力 | 优先解决慢点。工具改造只服务已观察到的采集障碍。 |
| 多种优化路线都可能成立 | 根据实测慢点先验证最直接、最易维护的一种，不同时铺开。 |
| 新包替换旧包 | 核对实际加载身份并完成约定的产物验收；减少换包频率，不能跳过身份检查。 |
| 性能结果不明确或质量不合格 | 按预先确定的停止规则记录，不删慢样本、不持续寻找漂亮成绩。 |

检查应与改动和风险相称。新增测试必须回答“已有证据为什么不足”，不能只因为能够写出更多测试就继续添加。

## 6. 所有新增测试和额外步骤，都必须接受时间约束

**任何新增动作开始之前，先写清四件事：解决哪个已发现的缺口、预期得到什么结果、全部需要多久、何时停止。** 这通常只需要台账中的一行，不成为新的审批流程。

“全部需要多久”必须包括分析、实现、构建、测试运行、处理失败、必要重验和记录交付。不能只计算当前命令的预计执行时间。一次很小的修改如果使最终包改变，其重验成本也必须计算。

| 判断 | 执行决定 |
| --- | --- |
| 直接保护必须达到的功能、安全或性能标准，且完整成本装得下 | 在计划内执行，使用最小充分检查。 |
| 属于可选优化，收益有实测依据，且不会挤占最终验收与交付 | 在分配的迭代时间内执行，到停止点作决定。 |
| 不能直接缩小缺口，或已有证据足够 | 不新增，复用或记录到后续任务。 |
| 必须完成，但剩余时间装不下 | 先说明缺口与最小方案；不能先执行再默认超额，也不能擅自降低标准。 |

多个小测试的成本也要累计。不能把“每次只花一点时间”作为无限添加的理由。必要检查不能静默省略，可选工作也不能挤占必要检查；两者冲突时，应先停止可选工作。

## 7. 下一次怎样做到快速优化、快速迭代

下面是轻量执行顺序，不额外建立框架或繁杂流程。各步分钟数在具体项目中根据实测确定，不使用本次复盘虚构一套通用时间比例。

| 步骤 | 必须得到的结果 | 停止或进入下一步的条件 |
| --- | --- | --- |
| 1. 固定目标、当前版本和必须达到的标准 | 清楚知道本轮只改善什么，已有证据是什么 | 没有与目标相关的明确缺口，不进入广泛调查。 |
| 2. 短测定位，并核算完整验收成本 | 一个实测慢点；完整测量、修复和交付的可行预算 | 不可行时先调整计划或向用户说明，不先大量开发。 |
| 3. 修改一个主要慢点 | 一个小而可维护的候选；保留可回退版本 | 到步骤时间边界必须选择保留、撤回或改走更直接路径。 |
| 4. 定向验证并作采用决定 | 受影响行为正确，开发性能比较有信息增益 | 无可靠收益就撤回；无新信息就停止同一路径。 |
| 5. 冻结候选，完成约定验收 | 同一实际产物的完整结果和明确缺口 | 冻结后只处理阻碍交付的必要问题，可选提速放到下一轮。 |
| 6. 交付并结束 | 版本、成果、通过项、未通过项、实际用时清晰 | 达到结束条件即收尾；剩余预算不自动转成新任务。 |

开发比较用于快速筛选方向，最终验收用于支持交付结论。两者可以复用输入和脚本，但不能让每个实验都承担最终验收的全部成本，也不能把开发比较当成正式通过。

优先读取原生数据、减少Python临时对象和重复类型判断，确实是本轮有效方向。仍应由真实调用的慢点决定优先级；不要为了“更原生”引入难以维护的类型布局依赖，或者替换已有安全路径却没有足够收益。

## 8. 时间与30分钟自查怎样真正约束执行

保留每30个累计有效分钟的简报；步骤首次超时也立即自查。这些检查使用已有结果，通常保持在90秒内，不为汇报额外跑测试。

每次只明确：新增的有效结果、距离交付还缺什么、已用和剩余时间、下一步及其停止点。完成百分比继续按通过的验收分值计算，不能按用时、代码量或测试次数计算。

出现超时、重复失败或长期没有缩小缺口时，回答：

> 相比继续当前工作，有没有更直接缩小目标缺口的下一步？如果有，为什么还没推进？

自查必须形成执行决定。当前路径有效且成本仍可容纳，就继续；同一路径没有信息增益，就停止；替代方法更直接，就作最小调整。不能仅记录一次“方向正确”然后继续没有边界的分析或测试。

**计划中的单步时间不是可以无限续延的建议，项目总时间也不是需要用完的额度。** 阶段调配只能在既有授权和剩余预算内进行，并保留实际差额。总额或截止时间变化需用户决定；用户增加时间后，也应重新评估方法效率，而不是机械延长原路径。

最终验收和交付时间必须提前保留，依据完整控制、完整正式周期的实际速度估计。若采用新候选将迫使整套重验，就先比较新增收益和完整成本，再决定是否值得变更。

## 9. 值得保留的经验

- 短批次、线程CPU与实际经过时间核验、紧邻完整配对、平衡顺序和失败回队，使负载波动下仍能逐步收集可信数据。保留这套自动判定能力，减少人工介入。
- 有效慢样本继续保留，数量和停止规则提前确定；结果不明确就报告不明确，不能以筛样本或反复选值换取通过。
- 直接减少对象创建和重复转换，比复杂的理论优化更容易获得可维护的收益。先用实测确认，再深入优化。
- 没有收益的实验撤回，保留真实失败证据；冻结产物与实际加载身份一致，避免旧成绩证明新代码。
- 同类比较、不可变值和明确拒绝无法表达的转换，改善了API可靠性；对外文档继续面向调用者解释实际行为。
- 用户要求停止时及时收尾，清楚区分“采用现有成果”和“原完整验收通过”。这项诚实边界应继续保留。

## 10. 后续开发的核心约束

> 严格遵守项目计划时间，以快速优化、快速迭代为核心。每次只推进一个有实测依据的主要缺口；所有新增测试、调查、工具改造和额外步骤，都计算完整成本并设停止条件。复用已有有效证据，减少没有信息增益的防御性扩展。优先保证必要功能、安全、验收和交付；可选优化不得挤占这些时间。到时间边界必须作决定，不默增预算、不降标、不把未完成写成通过。

现有日志不能精确量化哪些分析分钟可以全部消除，也不能证明按这些方法必然能在原8小时内完成。但它足以证明：减少决策周转、降低最终候选变更频率、提前核算整套采集成本，是后续最直接的效率改进。
