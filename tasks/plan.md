## 一、项目目标与当前起点

**用 Rust 实现 cyTimes 3.1.0 Delta 的完整 Python 功能，保持已有调用方式与结果，在真实 Python 调用中达到约定的速度提升，并让数字处理、错误恢复和内存访问更可靠。交付可安装、可重建、可验证的 rsTimes 包。**

“完整功能”指本项目已经调查出来的构造参数、属性、方法、运算、类型交互、子类、异常和保存复制行为，不代表承诺无限种输入或所有未来解释器；每个已识别的不同规则必须有验收证据，未知失败不能被测试数量掩盖。

### 用到的少量名词

- wheel：可以直接安装的 Python 包；这里必须含真正编译后的 Rust 扩展。
- sdist：源代码包，用户可以从它重新构建安装包。
- 对照检查：给两个版本相同输入，并排比较结果；本文 T 命令做的就是它。
- i32/i64：32 位/64 位有符号整数，可接受范围有限，过大必须按约定报错或回绕。
- hash：字典、集合用来寻找对象的数字；相等对象理论上应有相同值，旧版存在已记录缺陷。
- NotImplemented：Python 的“交给对方尝试”标记；它不同于直接抛错。
- 回调：Rust 运算中调用一个 Python 方法，例如 dateutil 的 normalized()。
- ABI/Cython 二进制兼容：其他已编译程序是否还能直接使用旧对象的内部布局；Python 方法同名不代表这部分兼容。

## 三、进度怎么算、什么才算完成

### 唯一计分规则

本计划有 **33 个验收单元，合计 100 分**。分值代表约定交付成果的权重，不是工时、代码量、测试数或成功概率。

- 每单元只按“未通过=0 分、已通过=该单元全部分值”计分；写了代码、测试数量增加或口头说差不多都不计分。
- 全项目完成率 = 已通过单元分值之和 / 100 × 100%。
- 阶段完成率 = 该阶段已通过分值 / 该阶段总分 × 100%，显示一位小数。
- 每单元自身完成率只有 0% 或 100%；进行中的工作内容和卡点用文字写明，不能虚估成 80%。
- 例如：S1.1–S1.3 通过，得到 8 分：项目 8%，阶段一 80%；S1.4 通过后项目 10%，阶段一 100%。
- 33 个单元全部通过才是 100%，功能、性能、安全、安装四种结果还要同时通过，不得“功能做完”就宣称项目结束。
- 分值与分母固定。不能通过删任务、跳测试、调低目标使进度上升。用户明确增减范围后，保存旧版与新分值、说明进度变化，不静默重算。
- 若后续改动使旧证据失效，对应单元退回“需修正”，暂时扣除分值；修复并补足受影响证据后恢复，不要求无关任务重做。

### 台账状态和证据

唯一状态文件是 [tasks/todo.md](todo.md)。本文件给要求；todo 给状态；证据给事实，不创建重复看板。

允许状态：未开始、进行中、待验收、受阻、需修正、已通过。只有“已通过”能勾选并得分。每次交接填写：当前 ID、已经完成的具体内容、最后一次结果、下一项动作；通过时补日期、证据路径、源文件状态指纹与 wheel hash（若使用 wheel）。

每份轻量证据至少写：任务 ID、环境和依赖版本、涉及输入/接口编号、执行命令、退出状态、通过/失败/批准差异、产物指向、尚缺证据。原始计时保存于 benchmarks；大型构建产物保存在临时目录或 CI 产物，不塞入进度记录。

“通过”包含三件事：本单元标准满足；验证实际执行且成功；产物与证据存在。尚未安装、runner 不可用、用例被跳过、批准未收到的相关行为均不能通过。

### 随时可查的进度与时间估算

用户随时询问进度时，读取最新 todo 与有效证据，核对当前工作树及相关产物是否使证据失效，分别报告：总项目已得分/100 和百分比；八个阶段各自已得分/阶段分值和百分比；当前单元及状态；最近通过结果；当前阶段与全项目剩余时间区间；估算依据、阻碍与下一动作。未开始的阶段为 0%，已经通过的阶段为 100%，不得把总体 40% 误称各阶段都完成 40%。无法核对的状态注明“待复核”，不把旧台账冒称即时确认。

版本 5 沿用所有 33 个单元的原“目标时间额度”，总计 600 分钟，另留 120 分钟修复余量，总目标 720 分钟。每单元记录所属阶段、累计目标结束时间、预算依据和主要不确定性。单元预算是安排工作和触发检查的依据，不是实测完成时间；真实剩余时间从开始实施后的证据校正。当前不能把 12 小时当确定完工预测。

计时从已授权的实施开始记录 T0，本轮及此前规划不计入，不追扣无法可靠核对的历史时间。“有效工作分钟”采用项目有效经过时间：必要阅读、实现、正常安装/下载、编译、功能验证、性能复测、修复、记录、简报和最终交付均计入。只有实际暂停，或必须等待批准且未继续推进项目的区间单独记录；等待答复时仍推进独立工作，该区间照常计入。不能将正常构建等待隐藏为“非工作时间”。不自动启动其他 agent，也不以多人投入或工具耗时相加冒充项目经过时间。

例如构建运行 20 分钟，其间同时整理本项目记录，总计仍是 20 分钟；工具耗时可作诊断记录，不再加到总工时。时间来自实际时钟；无法核对的区间注明估算、依据和误差范围，不伪造精度，也不因未记录就计为零。当前未约定自然日期截止时刻；将来若另定日期与时区，须与有效时间预算分别记录，暂停不自动延后该截止时刻。

每个单元记录：目标额度、实际耗时、当前尚缺结果、剩余额度、证据和下一个动作；阶段与总项目分别加总。完成两个可比较单元后，结合真实耗时校正剩余预测，仍保留原目标线和任何调配记录。总分始终按通过证据计算，不按用时比例给分。

进入每个阶段前，利用已有有效结果更新该阶段和全项目的剩余时间区间，说明依据、主要不确定性及是否可能影响原目标线。近期下一单元详排到可执行；远期沿用既定范围、依赖、分值和额度，预测用范围，不重写已完成的 33 步或增加调查轮次。更新预测不是增加预算，也不能把原目标分钟改成预测区间来消除落后。

每段有效时间只归属一个单元，包括早期性能工具准备、验证和简报，不能在两个阶段重复计时。阶段实际用时包括该阶段使用的修复时间；修复余量的“已用”只是说明额度来源，不是另一份工时。总实际用时只加总八阶段实际用时，不能再加一次修复余量已用。剩余总额度=720−累计有效用时，修复余量剩余=120−已记录的余量使用，两者分别报告。

余量只用于达到现有门槛的具体缺陷、工具安装/首次编译超时或性能问题。某单元提前完成，释放未用额度；超时需记录从何处调配及原因。不能悄悄重新计时、重画目标线、增加总预算或删未通过项。用掉余量 60 分钟时必须说明 12 小时目标是否仍可达及其依据。

正式进度报告同时给出：验收百分比、耗时/额度、距离原目标线的差距、剩余时间预测及置信度。12 小时到点仍有门槛未过时，报告真实完成率、明确缺口和最小追加工作估算；不将“达到时间额度”称为完成。

### 长任务启动前的余量检查

构建、安装、完整功能检查、正式性能测量或其他可能长时间运行的动作，启动前顺手核对：当前剩余总额度和本阶段可用额度（含已记录调配）；预计运行时间与不确定性；能否安全停止、保存或恢复；必要收尾、记录和交付需要的时间。引用已有有效耗时判断即可，不为这项检查另建工具、重复试跑或增加例行批准。

12 小时保持冲刺目标，不自动改成强杀任务或强制结束项目的截止时刻。意外超时在首次安全返回边界报告，只完成必要安全收尾或到安全停止点，并记录超出时间；不把安全收尾当作已获新增预算或无限继续的授权。到点未过门槛时如实交接，原额度之外的新工作须取得相应追加授权。本轮不追扣规划时间，不改变既定计时起点。

### 固定检查与偏离纠正

在工具调用之间的安全边界检查：每 30 个有效工作分钟、单元完成、阶段结束、同一失败经有理由复测后重复两次、将耗用余量，或新风险已影响交付/时间目标时。30 分钟检查点按累计有效时间 T+30、T+60……计算，单元、阶段结束或重新规划不重置间隔。长编译用可返回输出的工具跟踪，不为了到检查点杀掉有进展的构建。检查、台账记录和简报通常合计控制在 90 秒内，超过则必须是正在解决的具体问题，不能展开新规划。

每次仅记录五类事实：当前任务/尚缺结果；已通过分值与证据；实际耗时/目标额度/余量；原目标线的当前差距；下一项必要动作。原目标线以 todo 的累计目标分钟及相应验收分值定义，不要求“花了50%时间就要完成50%”。未到某单元目标结束时刻的工作不按未完成判落后，进行中也不提前得分。

出现以下任一条件，视为需要纠偏检查，而非自动换方向或降低目标：

- 单元已超目标额度至少 25%，且超出至少 10 分钟。
- 阶段目标交付逾期至少 30 分钟；或连续两个 30 分钟检查点，已到期单元应得分与实际已得分相差至少 5 个百分点。
- 连续 60 分钟没有新增有效通过结果、可复现定位或明确缩小失败范围；同一失败已重复两次且没有新线索也触发。
- 已使用修复余量达到 60 分钟，或现有证据显示剩余时间不足以完成未过门槛。

这些是检查信号，不是机械判定失败或必须换方向。特别是 5 个百分点差距，要结合决定后续能否交付的关键步骤、下一验收点、缺口变化和剩余预测判断；分值暂未增加但已有可复现定位或失败范围缩小，仍可能在有效推进。原生对象机制、最终性能或安装等关键交付条件已受威胁时，立即报告，不等达到数值阈值；也不能用容易取得的其他分值掩盖关键阻碍。

纠偏时使用用户问题：**“相比继续当前工作，有没有更直接缩小目标缺口的下一步？如果有，为什么还没推进？”** 只输出简短决策摘要：当前缺口是什么；有没有更直接动作及其前置条件；继续/调整/报告阻碍的选择和理由；接下来可验证的结果。不要写长自述或详细内部推演。

若方向正确且失败范围正在缩小，继续当前必要动作，记录合理的额度调配。如果发现偏离，停止新增无关分支，保留已有成果，只调整到更直接满足当前目标的必要动作；不得为了多拿进度分转做容易的文档或回避核心缺陷。若缺失工具、数据或真实范围决定，说明阻碍并推进不受影响的必要工作。

最小调整只改变动作顺序、共用实现、验证组选择及 720 分钟内的额度分配。功能范围、异常约定、1.25/10% 性能门槛、安全要求与安装标准改变仍需用户决定；时间压力不是授权。保留原目标线、实际结果及调整理由，不以重新排期消除落后记录。

**每个 30 分钟检查点完成后，必须立即在当前对话发送用户可见简报。** 无论进度正常、分数未增加、继续原方向、需要调整或遇到阻碍，都要报告，不能只更新台账，也不等待用户询问。使用下面三段固定格式，保留原来的进度、实际推进、检查结果、时间、方向决定和下一目标六项信息：

1. **成果与检查：** 当前单元 ID/状态、本周期可验证成果及证据位置；没有新增分值时说明具体缺口是否缩小或仍无实质推进。对照原目标线判断正常、明显落后或受阻，并说明当前工作是否直接推进 Delta 的功能、性能、安全或安装目标；进行中不提前计分。
2. **进度与时间：** 总项目 X/100 分（X%）、当前阶段 y/z 分（Y%）；累计有效用时/720 分钟、剩余总额度、修复余量剩余及当前单元用时/额度。阶段或全项目剩余预测有变化时补区间和依据，缺少证据时写“尚不能可靠估算”。
3. **决定与下一步：** 明确“继续原方向”“作最小调整”或“有必要决定待用户处理”，给一句理由；说明接下来 30 个有效分钟优先缩小的缺口和可验证结果。需要用户决定时给推荐、影响及最晚需要决定的时点，不默改范围、门槛或原目标线。

简报首行标明检查时刻和所覆盖的有效工作时段。长工具运行跨过检查点时，在首次安全返回边界完成检查并简报，说明延迟原因；多个到期检查点合并说明覆盖时段，不补发没有独立检查事实的历史简报。单元/阶段等触发与 30 分钟检查相邻时合并报告；真实阻碍或重大偏离及时通知。按实际工具能力跟踪；没有经验证的后台计时或主动推送能力时不作该承诺，无法按点报告时说明限制并在恢复后的首个安全边界补报。没有新增成果也照常报告，不为使简报好看而增加测试、研究或文档工作。

检查表在 todo 保存，每次只加一行，并登记简报发送时刻。它是已授权开发期间的检查点约定，不建立后台定时任务或另一个看板；用户随时问时仍读取当前项目事实。当前实施未开始，不启动计时或编造首份开发简报。

### 5.2 性能验收：D3 已确定的首版完成门槛

参照对象：固定 cyTimes 3.1.0 安装包。参照环境：本机 macOS arm64、普通 CPython 3.13，固定依赖与 release 构建。它证明这个环境的速度，不保证所有机器都一样。

固定九组，组内具体输入在实现早期随功能一次锁定，S7 前不得根据快慢重新选择：

| 组 | 测量的用户调用 | 角色 |
| --- | --- | --- |
| B1 | 空、混合正负、绝对字段构造 | 核心 |
| B2 | 单个及整组属性读取、bool | 核心 |
| B3 | Delta±Delta、取负、abs；正负、抵消及绝对字段冲突 | 核心 |
| B4 | Delta 与 timedelta 的允许加减方向；正负微秒及带绝对字段 | 核心 |
| B5 | date/datetime 的普通、月底、跨年、带时区/fold、无变化返回；复用 Delta 和每次新建两种方式 | 核心 |
| B6 | eq、首次/缓存 hash、repr/str，分别报告 | 核心 |
| B7 | from_relativedelta 与相关运算；整值、分数、绝对字段和星期 | 互操作 |
| B8 | NumPy ns/us/D/M/Y 等不同换算路径的允许正反向运算 | 互操作 |
| B9 | 新包 pickle 读写、copy、deepcopy，分别报告；基础对象及带字典子类 | 保存复制 |

覆盖判断：九组覆盖了当前 Delta 主要公开调用的成功路径，可以作为首版通用性能比较。它不等于“覆盖实际用户使用量的某个百分比”：没有业务调用频率或真实负载，不能给出这个比例。错误输入、整数溢出、NaT 异常和畸形状态由对应功能/安全检查验收，不为提高性能覆盖数字反复计时；数组批量计算不属于 Delta 本次范围。

在 B5 内固定一个代表性组合调用：构造或复用 Delta → 应用到一组 date/datetime → 读取结果日期字段。两种方式分别计时并列明循环成本，原版和候选执行相同工作；不合并相同数据的重复样例，不再新增独立性能组。B6 区分首次与缓存 hash，B9 区分基础对象与实际子类，避免只测最快的路径。

每个代表输入的“速度比”=原版中位耗时÷候选中位耗时。1.25 表示同样调用量的候选耗时为原版 80%，即减少 20%，不能混淆“速度提高”和“耗时减少”。

组内以相同权重合成速度比；核心六组也相同权重，组合公式为 G=(r1×r2×r3×r4×r5×r6)^(1/6)。这样一个本来较慢的用例不会因为单次耗时大而独占结论；这是一份固定比较工作量，不宣称它代表真实用户使用频率。每项原始耗时始终单独列出。

已确定的完成门槛：

- P1：核心六组组合速度比 G≥1.25。
- P2：任一锁定的代表输入，候选中位耗时≤原版的 1.10 倍，避免用平均提速掩盖明显退步。
- P3：dateutil 与 NumPy 两组组合速度比≥1.00；保存复制按 P2 判定。
- P4：性能结果必须有功能结果和原始样本，候选使用最终 release 配置，不删除错误处理或特殊类型支持。
- P5/P6：原规则为7对≥100ms、两方自身波动≤5%、跨批次最快/最慢保守比较及一次噪声重测。2026-10-10用户授权改造，当前按下文短批次协议v2执行。旧规则及失败结果保留为历史，不追溯改判。

### 5.3 安全验收

S2：全部已识别的数字输入和中间计算都有确定策略。输入越界按原契约拒绝；D1 已确定：实际中间溢出或最终目标字段无法表示时明确抛 OverflowError，逐例登记与原版回绕结果的差异，不再保留回绕模式。日历允许临时越出年界，最终无效 Python 日期仍用原 ValueError。不能在开发模式报错、release 却静默改变结果。[Rust 官方整数资料](https://doc.rust-lang.org/std/primitive.i64.html)区分有检查和明确回绕运算，本版采用明确的溢出检查，D1 已确定。

S3：错误状态、异常回调和年界输入产生明确 Python 错误，不能让自有原生代码崩溃。原版可观察的失败后状态保持或逐例登记改变。任意 Python 回调本身可以运行用户代码；本计划不承诺阻止用户写无限循环或任意副作用。

S4：对象访问和 Python 回调不发生冲突；代表性子类及引用释放有证据。检查覆盖本次路径，不把有限释放检查说成所有情况下无泄漏，不为并发性能新增共享全局缓存。

S5：新 Rust/Python 依赖来源、锁定版本和已知漏洞核对完成，无未处理的可达严重风险；审查不能只看“扫描为零”就宣称绝对安全。工具缺失或离线导致没有数据时，安全步骤仍是未验收。

S6：保存读取只验证可信数据；说明 pickle 可执行对象恢复代码，不能声称用 Rust 重写后不可信 pickle 可安全加载。[Python 官方 pickle 文档](https://docs.python.org/3/library/pickle.html)明确指出该限制。不处理旧路径，不注入或冒充 cytimes 模块。

保留的 eq/hash、可变缓存、NaT 和多倍单位缺陷必须列在安全/兼容说明中。本次安全提升以具体的内存保护、确定数字策略和错误处理为依据，不以消除全部旧逻辑缺陷为虚假宣传。

### 每个工作单元的实际推进顺序

先读取本单元要求和对应冻结源码；在共享用例表中取现有输入或补齐原版结果；确认候选未实现或存在差异；实现最小必要路径；运行对应组；通过后记录证据与得分；立即进入下一个满足依赖的单元。

发现失败时：定位最小输入→修复相关路径→跑失败所属组及受到同一改动影响的已通过组。没有变化、新风险或预定采样目的时，不重复运行相同成功检查。完整功能检查主要在 S6.5 和最终安装产物执行，两次对象不同，目的不同；中途只在共享入口变更需要时运行，不逐小项全量重跑。必须重复的检查沿用上面的用途与停止规则，不以“不重复”为由省略正式采样或修复确认。

创建构造用例时不先研究所有 pickle 错误，写日期路径时不扩展 NumPy ABI 调研；接口未覆盖项留给明确负责的单元。这是限制同时展开的工作量，不是删除已识别必要规则。

### 命令接口约定

以下命令是执行计划中的约定，**tools/delta_check.py、benchmark 和 Cargo 目前不存在，必须由对应单元创建并实际验证后才能使用**。路径均相对项目根目录；环境放 .local/delta，需在实施中纳入忽略范围。运行器使用 pathlib 定位环境解释器；本版只验收 macOS，仍不手拼系统分隔符。命令示例中的本机解释器路径是已观察到的环境记录，工具实际读取已验证配置，不把此机器路径写死在库源码。

RUN_ID、WHEEL_PATH、SDIST_PATH 是待替换的示例占位，不是已存在的文件。RUN_ID 为本次运行唯一编号；每次原始结果写入新的目录，避免覆盖旧验证。Sx.y.json 是对应单元的证据索引，引用实际运行记录；执行状态仍只写 todo。所选 wheel、来源和 hash 一起记录，不按目录里“最新文件”猜测包。

B（开发轮次 release wheel）：S1.3 固定工具并生成 Cargo.lock 后执行，只针对本机解释器，复用同一编译缓存：

    maturin build --release --locked --interpreter /Users/jef/.pyenv/versions/3.13.3/bin/python3.13 --out .local/delta/wheels

输出的明确 wheel 路径交给 I 安装；源文件改变后旧 wheel 无效。S1.3 用实际固定版本的 --help 与一次构建验证命令，不根据计划文字冒称可执行。

B final（S8 构建最终完整产物；使用本次独立空输出目录，WHEEL_PATH/SDIST_PATH 替换为实际输出的明确路径）：

    python -m build --sdist --wheel --outdir .local/delta/final/RUN_ID
    python -m twine check --strict WHEEL_PATH SDIST_PATH

开发轮次不重复创建 sdist；最终 sdist 内容、干净重建、最终 wheel 的全功能和性能证据仍须齐全。[maturin 官方构建选项](https://www.maturin.rs/distribution.html)描述 release、指定解释器、输出位置及锁定依赖；命令在本机实施后才能算验证通过。

T（对应功能组）：运行器 --group 接受每单元给出的名称，例子：

    python tools/delta_check.py --group coercion --oracle-env .local/delta/oracle --candidate-env .local/delta/candidate --report tasks/evidence/RUN_ID/coercion.json

T all（全部既定功能）：

    python tools/delta_check.py --group all --oracle-env .local/delta/oracle --candidate-env .local/delta/candidate --report tasks/evidence/RUN_ID/functional.json

I（干净安装和原生加载；WHEEL_PATH 是本次选定 wheel 的实际路径，开发轮次从 B 输出取得，最终阶段从 B final 或重建输出取得）：

    python tools/delta_check.py --group installed --wheel WHEEL_PATH --candidate-env .local/delta/candidate --report tasks/evidence/RUN_ID/installed.json

E（保留原有测试，候选解释器以 -I 从安装包运行现 tests/test_rstimes.py）：

    python tools/delta_check.py --group existing --candidate-env .local/delta/candidate --report tasks/evidence/RUN_ID/existing.json

A（包内容，来源归属及源码包重建）：

    python tools/delta_check.py --group artifacts --wheel WHEEL_PATH --sdist SDIST_PATH --candidate-env .local/delta/candidate --report tasks/evidence/RUN_ID/artifacts.json

P（正式性能，--group 可只选受影响的 B1…B9，all 为全部）：

    python benchmarks/delta/bench.py --mode formal --group all --oracle-env .local/delta/oracle --candidate-env .local/delta/candidate --output benchmarks/delta/results

P quick（开发复测；下面两个结果路径在首次运行后由工具输出，示例当前尚不存在）：

    python benchmarks/delta/bench.py --mode quick --group B1,B5 --oracle-env .local/delta/oracle --candidate-env .local/delta/candidate --baseline benchmarks/delta/results/baseline.json --compare-to benchmarks/delta/results/previous/raw.json --output benchmarks/delta/results

首次 quick 没有基线时省略 --baseline，由工具建立所选组基线；没有上次候选时省略 --compare-to。正式模式不把 quick 的缓存计时当原版当次样本。

Rust 整数核的必要检查与格式检查：

    cargo test --locked
    cargo fmt --check
    cargo clippy --locked -- -D warnings

整数端点在开发和 release 至少各验证一次：如相关策略/整数代码发生改变，重跑相应 cargo test 与 cargo test --release --locked。这用于捕捉编译模式差异，不因“Rust 有检查”就重复所有 Python 行为组。
